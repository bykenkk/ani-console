# ANI Console API 对接流程

本文档约束 ANI Console 新增或调整接口时的契约核对、代码落位和验证流程。它不复制维护后端端点目录；迁移期以 `ani-governance` 为目标后端、`ANI` 为存量后端，具体路径、字段和行为始终回到对应权威后端的契约与实现核对。

GitNexus 使用方式遵循 [AGENTS.md](../AGENTS.md#gitnexus)。

## 契约核对

### 迁移期后端归属

`ani-governance` 与 `ANI` 是两套独立系统，接口契约与资源 ID 不兼容，不要求新接口兼容旧请求。当前处于后端能力逐步迁移、替代接口持续补充的阶段，其他页面及关联能力尚未全部具备新接口，不能假定新旧两套 API 同时可用。迁移应以逐项补齐并核对 governance 的正式能力为前提，不以旧接口作为新系统的兼容层或缺失能力的兜底；旧代码和契约仅作为迁移参考及待替换内容保留，其存在不代表旧服务仍可调用。权威后端的指定用于核对契约，不构成接口已部署、可联调或可跨系统使用的保证。

1. 已明确迁移的接口以 GitNexus 索引 `ani-governance` 为唯一权威实现；`ANI` 只用于迁移前后差异核对，不得以旧实现覆盖新契约。密码登录及其 Cookie 刷新凭证语义属于已迁移范围。
2. 尚未明确迁移的接口仍以 `ANI` 为当前权威实现，同时查询 `ani-governance` 判断是否存在迁移实现；不得仅因目标仓库出现同名路由、模型或未完成代码就认定已经迁移或部署。
3. 两个后端的路径、字段、认证、幂等、错误或副作用存在差异，或无法确认接口归属时，必须停止相关对接并请用户确认，不得自行混用两套契约。
4. 后端尚未部署或用户明确禁止调用接口时，不得发送探测、联调或验证请求；只执行静态契约核对与前端检查，并在结果中列出未验证的运行时行为。

### Governance HTTP 接口约定

经 `ani-governance` 向前端提供的新增或修改 HTTP JSON 接口遵循以下约定。存量接口按明确范围迁移，具体端点按 Core 或 Services 流程核对权威契约与实现；VPC 已采用页码分页，其他领域的接入状态须分别核对。

#### 请求与响应

- 查询参数放在 URL 中，创建、修改的业务数据使用 JSON 请求体；业务字段及请求体结构以接口定义为准，不自行增删 `data` 包装。
- 普通详情直接返回资源对象，普通列表直接返回 `items/total`，不增加资源名称、外层 `data` 或统一的 `code/message/data` 成功包装。
- 写入需要返回单个资源时使用详情对象结构；无业务结果时返回 `{}`，`204` 不返回响应体。部分更新省略字段表示保持原值，清空必须显式表达；异步受理保留任务或操作信息，不把受理成功视为业务完成。
- 使用 HTTP 状态码区分成功与失败，不将失败包装成 `200`。错误体包含 `code`、`reason`、`message`，业务分支依据 HTTP 状态和 `reason`，`message` 仅用于说明。存在 `X-Request-ID` 或 `metadata.request_id` 时保留用于排查，不假定每个错误都具有请求 ID；前端统一通过[公共请求层](#公共请求层)处理。
- 64 位整数使用十进制字符串，时间使用 RFC 3339 字符串；字段名、枚举和其他类型按接口定义使用，不自行转换大小写或将所有 ID 转成数字。组合结果及列表的 `observation` 等元数据保留完整结构；导航树、权限或容量快照、统计和日志按业务结构处理，不因内部有数组就改成普通分页列表。

#### 列表分页核对

| 项目 | 必须满足的规则 |
|------|----------------|
| 请求参数 | 只使用 `page`、`pageSize` 分页；`page` 从 `1` 开始，默认 `1`；`pageSize` 默认 `20`，范围为 `1` 到 `100` 的整数。两个参数分别使用独立默认值；VPC 的 `page` 范围为 `1` 到 `4294967295`，其他接口的页码上限按各自声明核对。筛选与排序参数由接口声明。 |
| 参数校验 | 分页参数为单个规范十进制正整数；显式传入零、负数、空值、前导零、小数、重复参数或越界值必须返回 `400`，不得静默修正；未声明的查询参数也返回 `400`。公共查询数组序列化规则不代表分页参数允许重复。 |
| 响应结构 | `items` 为当前页数组；`total` 为当前调用者有权查看且符合筛选条件的实际总条数，JSON 类型为十进制字符串，不得用当前页长度冒充总数。类型声明保留字符串；展示或分页控件需要数值时，信任后端返回合法数字字符串，直接使用 `Number(total)` 转换，不额外添加合法性、非负或安全整数检查。 |
| 直接跳页 | 支持首次请求直接访问任意合法页，无需预先访问前面的页；不得使用游标循环或预拉取前页模拟页码分页。 |
| 空列表与超界页 | 无匹配数据时返回 `items: []`、`total: "0"`；页码超过最后一页时仍返回空数组，但保留实际匹配总数。 |
| 排序与一致性 | 后端先确定排序再分页，主排序相同时用唯一键兜底；列表与计数使用相同可信租户、权限和业务筛选范围，并在同一数据库只读快照读取。连续请求间数据可能变化，不将分页视为冻结结果。 |

VPC 专属核对项：`name` 去首尾空白后区分大小写精确匹配；`state` 按接口定义筛选，不传时排除 `deleted`；固定按 `created_at DESC, vpc_id DESC` 排序，不开放任意排序字段。其他领域保留各自明确声明的筛选、排序和授权条件，不直接套用 VPC 业务规则。

#### 不合规时中断与恢复

1. 对接新接口或修改 `ani-governance` 接口时，发现契约、实现或允许联调时的实际行为不满足上述约定，必须立即中断受影响的对接修改，先向用户说明具体接口、期望规则、实际差异、证据及对前端的影响；不得先实现兼容再补报，也不得通过字段重命名、响应拼装、伪造总数或遍历分页掩盖差异。
2. 只有相关问题已完成修改并重新核对符合约定，或用户明确确认绕过具体差异后，才能继续受影响的对接修改。仍有差异或待迁移事项时，按[迁移标记与保留边界](#迁移标记与保留边界)在对应代码旁标注，不将其他接口、其他差异或沉默视为一并授权；绕过上述约定不免除必需索引核对及禁止调用未部署接口等既有约束。
3. 中断时按[迁移标记与保留边界](#迁移标记与保留边界)添加占位并保留旧调用，不推进受阻实现；不能以添加标记代替用户明确确认。

### 迁移标记与保留边界

- 迁移阶段未迁移或迁移不完整的接口、字段、参数及关联组件、入口，以及因不合规中断的接口、类型或调用位置，必须根据实际情况在对应实现旁使用 `TODO` 或 `FIXME`，不要求成对添加；不得只在统一导出入口添加笼统标记。
- `TODO` 用于当前按现有契约工作的待迁移、待完善或待验证事项，写明后续工作及触发条件；`FIXME` 用于当前实现中需要修正的问题，写明具体问题、影响及修正方向。标记只描述技术事实、适用范围和后续事项，不记录授权经过或对话过程；具体事项在对应代码旁维护，不在规范文档中重复记录。
- 恢复对接后仍有差异或待验证事项时保留标记，完成修正并验证后才能移除；未部署或禁止调用时保留运行时验证 `TODO`，不得以静态核对替代联调结论。
- 已对齐部分按新契约接入；未对齐部分保留原组件、入口、请求契约及实例类型等业务参数和旧调用，不得因公共组件迁移或新接口不合规而删除、隐藏或改变未迁移功能，也不得通过改名、类型断言或字段拼接伪装为新接口。
- 保留旧实现和调用，是保留其所属旧系统的存量功能及后续替换依据，不授权将 governance 资源 ID 交给旧接口、用旧详情补齐新资源字段，或在新接口失败/缺字段时自动回退旧系统。新系统未提供替代能力时按未完成迁移记录并按实际情况保留 `TODO` 或 `FIXME`；同一资源的读写与关联必须遵循其所属系统的正式契约，不能通过混合两套响应拼成已迁移功能。
- 用户明确指定迁移范围或标记方式时，按指定范围执行，不额外添加兼容分支或无实际问题对应的 `FIXME`。

### 资源创建、删除的 task 接口统一暂缓对接

- 所有资源创建、删除涉及的 task 查询、轮询及任务跟踪弹窗，本阶段统一暂缓对接，后续统一调整；在对应实现旁保留后续接入的 `TODO`。
- 异步创建、删除请求受理成功后，关闭提交弹窗（如有）、刷新相关列表并提示“创建已提交”或“删除已提交”；详情页删除提交后按既有交互返回。

### Core API

1. 开始对接前，先通过 GitNexus 查询索引 `ani-console对接文档补充`，确认是否存在测试环境已部署、代码尚未合并期间的临时说明。
2. 按迁移期后端归属查询 `ani-governance`、`ANI` 或两者：在 `ani-governance` 核对 protobuf HTTP 映射、生成处理器、请求/响应模型、中间件及实现流程；在 `ANI` 核对 Core OpenAPI、路由处理器、请求/响应模型及相关实现流程。
3. 按[完成检查](#完成检查)执行联调或记录未联调项。

未查询接口补充索引不得开始 Core API 对接。补充说明、权威后端契约与实现或测试环境表现存在差异时，不得自行选择其一或根据另一后端及前端旧代码推断，必须停止相关对接并请用户确认。

### Services API

1. 按迁移期后端归属查询对应后端索引，核对 Services OpenAPI 或 protobuf HTTP 映射、网关注册、路由处理器、请求/响应模型及实现流程。
2. 当前 `ani-console对接文档补充` 的强制前置规则只针对 Core API；若查询命中与目标 Services 接口直接相关的补充内容，也必须纳入核对。
3. OpenAPI 已声明但网关未注册、实现尚未开放或测试环境行为不一致时，保持未接入或明确空态，并请用户确认后续口径。

前端不保留 Core 或 Services 的整份生成式 schema 快照。模块内 TypeScript 类型只提供编译期约束，不代表运行时校验，因此每次接口调整仍必须重新核对后端契约。

## 模块与类型落位

- 请求函数与接口类型统一放在 `src/api/<domain>/`，页面、路由、组件、Hook 和 Store 不得直接导入 Axios 或 `src/api/request.ts` 拼装平台请求；页面、路由和组件不得出现 `coreRequest`、`servicesRequest`、Axios 平台请求或 `idempotency_key`。
- 简单领域使用 `index.ts` 与 `types.ts`；包含多个独立资源的领域按资源拆分文件或子目录，再由领域 `index.ts` 汇总公开接口。
- 页面提交类型命名为 `*Input`，不得包含 `idempotency_key`；API 内部最终请求类型命名为 `*Request`，需要幂等时在这里加入 key。响应、列表参数及资源记录使用具有业务含义的稳定名称。
- API 模块遵循[公共请求层](#公共请求层)的返回值和异常约定，不持有 React 状态，不包装或改变 `useQuery`、`useMutation` 的行为，也不直接操作 Query Client；查询与缓存职责遵循[页面接入](#页面接入)。

### 创建与操作提交的返回值

- 普通资源创建流程及操作类 `POST`、`PUT` 提交默认丢弃响应体；业务 API 等待请求完成后返回 `Promise<void>`，调用方不解包、映射或依赖提交返回的资源、task 等数据。丢弃响应体不改变请求等待与异常处理。
- 提交成功后，通过对应列表或详情查询刷新资源数据，不依赖写入响应更新展示。

## 公共请求层

| 能力 | 使用方式 |
|------|----------|
| Core API | `coreRequest`，基础路径为 `/api/v1` |
| Services API | `servicesRequest`，基础路径为 `/api/v1/svc` |
| 外部预签名地址 | `externalAxios`，不安装平台认证拦截器 |

- `coreRequest` 与 `servicesRequest` 默认要求登录并注入平台访问令牌；只有登录、令牌交换等公开端点显式传入 `auth: "public"`。
- 受保护请求返回 401 时由公共层执行单飞令牌刷新并重试一次；业务 API 和页面不得自行刷新令牌或重复实现 401 重试。
- 迁移期刷新凭证按权威契约传递：`ani-governance` 使用 `HttpOnly Cookie` 时必须启用凭证请求且不得把 Cookie 中的 refresh token 复制到前端状态或请求体；仍由 `ANI` 承载的旧链路可以继续使用其已声明的 body 字段。公共层必须兼容两种已确认契约，不得让业务页面判断后端来源。
- 公共请求层直接返回 `response.data`（HTTP 响应体），204 或空响应按 `undefined` 处理。业务 API 按用途返回查询结果或丢弃写入响应，并通过异常报告失败；不要求页面重复解包，不恢复 `{ data, error }` 双通道，Governance 普通响应体不再按内层 `data` 解包。
- 查询数组序列化为重复参数；`null` 和 `undefined` 不进入查询字符串。
- 请求失败统一转换为 `ApiError`，保留 `status`、`code`、`requestId`、`details` 和原始响应上下文，以及 Governance 契约中的 `reason`、`message` 信息。`ApiError` 是请求错误的唯一结构化模型；页面不得自行解析 Axios 或原始响应错误结构，也不得新增 `ApiErrorAlert`、`showApiError`、列表错误通知 Hook、公开的通用错误解析对象或其他平行错误解析与反馈辅助函数。少数需要按契约中的状态或业务错误标识映射文案的场景，先判断 `error instanceof ApiError`；Governance 的判断依据遵循[请求与响应](#请求与响应)。
- 需要取消的请求透传 `AbortSignal`。Axios 取消保持为取消错误，以便幂等层识别并重置作用域。

## 幂等写请求

- 所有 POST 及有副作用的 PUT/PATCH 都必须先核对权威后端声明的幂等机制；契约支持幂等时由业务 API 模块管理，即使 POST 语义偏读取，也不得因页面用途自行跳过。契约未声明幂等字段或 Header 时不得自行追加 `idempotency_key` 或 `Idempotency-Key`，并在变更结果中记录该接口未由前端补充幂等。
- 每个使用 body `idempotency_key` 的独立写操作在模块作用域创建 `createIdempotencyScope`。固定依赖至少包含请求方法；多阶段流程的各写步骤使用独立作用域，不共享 key。
- 页面先构造不含 key 的 `submitData`。影响请求身份但不在 body 中的稳定参数，例如资源 ID、文件指纹或操作类型，通过 `runtimeDependencies` 传入；路由模板和实际 URL 不作为依赖。
- 常规写请求使用 `runIdempotentRequest` 注入 `idempotency_key`。相同依赖和提交内容的普通失败重试复用 key；提交内容或依赖变化时生成新 key；请求成功或 Axios 取消时重置。
- DELETE 默认不套用上述 body 规则。若后端契约明确要求 DELETE 幂等，应按契约使用 `Idempotency-Key` Header 等指定形式，不得自行向 body 增加字段。

幂等 key 只能由公共幂等库通过外部 `uuid` 包生成。业务代码不得直接生成 UUID、手工拼接 key、把 key 放回页面状态，或从页面调用作用域的 `reset()`。

## SSE 与预签名上传

- SSE 请求仍从对应业务 API 模块发起，使用 Axios fetch adapter、`responseType: "stream"` 和 `AbortSignal`，返回 `ReadableStream<Uint8Array>`。领域组件负责协议解析、去重、重连和界面状态。
- 预签名上传分为平台侧预约/完成请求与外部文件传输。平台请求继续使用 Core 或 Services 客户端并遵守幂等规则；外部地址只能使用 `externalAxios`。
- 外部预签名请求不得携带平台 JWT、平台 Cookie 或公共客户端默认 Header。只有后端契约为该上传会话返回的专用 Token、Content-Type 等 Header 可以显式加入。
- 外部传输错误通过 `toApiError` 归一化；需要支持取消的上传或轮询阶段必须复用调用方传入的 `AbortSignal`，不得在中途重新创建互不关联的取消作用域。

## 服务端筛选与分页

- 业务列表及关联选择器的搜索、租户范围、角色范围、排除条件、排序和分页统一由后端执行，后端返回与全部筛选条件一致的记录和总数。
- 前端只传递已核实的查询条件并展示结果；不得对接口结果二次筛选、截取分页、重算总数，或先查角色等关联资源再在前端求交集、拼接 ID 来补偿后端筛选缺失。
- 关联选择器必须关闭组件内置的本地选项过滤，搜索和排除条件发送到后端；树形关联应由后端处理排除自身及后代、避免循环等业务规则。
- 后端缺少所需筛选能力时，列出对应接口、组合条件、空结果及分页语义，交由后端完善契约；契约确认前默认保留未接入状态，不猜测参数或伪造空列表。用户明确要求先接入已有查询能力时，可暂用已核实的服务端条件，必须按[迁移标记与保留边界](#迁移标记与保留边界)选择 `TODO` 或 `FIXME`，说明缺失条件、当前数据范围及补齐条件；仍不得使用前端筛选补偿。
- 表单字段显示、只提交实际编辑字段等本地表单逻辑不属于接口结果筛选；可以保留。

### 分页与选项加载

- 禁止前端为本地筛选、分页、导出或下拉选项自动连续或并发拉取多个服务端分页并汇总为全量列表；API 模块、Hook 和组件均不得实现此类 `listAll*`、游标循环、递归或批量分页请求。无需服务端翻页的列表直接请求一次，不传 `limit`，不得以固定大 `limit` 替代全量加载；有明确服务端分页交互时，每次只请求当前页，后续页由用户翻页或“加载更多”操作按需请求。除下述选项数据约定外，需要全量数据的能力应由后端提供明确接口，不得通过自动遍历分页模拟。
- 页码分页参数统一复用 `src/api/types.ts` 的 `PageParams`；`CursorPageParams` 已标记为废弃，仅供后端改造未完成的过渡调用保留，不据此批量改写尚未迁移的接口。
- 当前阶段，下拉等选项数据临时仅取前 100 项作为选项集合，不代表接口保证返回全部资源；超过 100 项的选项暂不可见。支持 `page/pageSize` 的选项请求统一通过 `src/api/pagination.ts` 的 `withFirst100` 包装已有列表函数，注入 `page=1`、`pageSize=100`，原样传递业务筛选参数、`signal` 和响应。调用方不再散写固定分页参数；查询键保留业务用途与筛选条件，并通过 `options` 标识与普通列表分页区分。包装方法必须保留后续优化和移除固定分页策略的 `TODO`。不额外添加上一页、下一页或加载更多按钮，也不自动拉取后续页；此临时策略仅适用于选项数据，不改变普通表格分页。新增或迁移的选项请求只允许使用 `page/pageSize`；`cursor/limit` 分页请求视为废弃契约，不得继续接入、复制为示例，或通过参数转换包装成新契约，现有过渡调用按下一条保留。
- 现有仍使用 `cursor/limit` 的请求属于后端分页改造尚未完成期间的临时过渡实现，不代表最终对接方式。遇到或修改此类调用时，应在对应实现旁按实际情况添加 `FIXME` 或 `TODO`，说明临时保留的原因，以及待后端完成后迁移至 `page/pageSize` 的事项；过渡期间保留现有调用，不将其视为已完成迁移，也不扩散为新的对接方式。

### 公共分页状态与迁移

- `src/hooks/useListPagination.ts` 统一管理正式页码分页的页码与每页条数；筛选 scope 改变、修改每页条数或主动重置时回到第一页。查询函数、缓存键、反馈与资源刷新由页面或领域组件维护，参数类型复用 `src/api/types.ts` 的 `PageParams`，表格总数取对应响应的真实 `total`，不通过游标预取模拟跳页。
- `src/hooks/useCursorPaginatedQuery.ts` 仅供后端尚未迁移的游标接口过渡使用，封装当前页查询、已访问游标及公共表格的 `legacy-cursor` 配置。调用方按原契约映射游标字段并提供业务查询键和错误反馈；查询 scope 或每页条数改变时清空游标链，每次只查询当前页，不显示总数、总页数或任意跳页。
- 分页标记按[迁移标记与保留边界](#迁移标记与保留边界)选择 `TODO(pagination-migration)` 或 `FIXME(pagination-migration)`，说明当前分页契约、需要修正的问题或后续迁移条件。后端完成正式页码契约后，调用方改用 `PageParams` 与 `useListPagination`，使用真实 `items/total`；所有过渡调用迁完后，再移除游标 Hook、`CursorPageParams` 和表格 `legacy-cursor` 模式。不能仅改前端参数名称宣称迁移完成。

## 页面接入

- 服务端请求状态、缓存和失效由 TanStack Query 管理；查询按页面或业务组件落位，查询和 mutation 通过领域 API 函数发起，mutation 只提交无 key DTO。反馈渠道、meta、稳定 ID、请求状态展示及错误呈现统一遵循 [UI 开发约定](./UI-CONVENTIONS.md)。
- 复用资源操作及其成功后的缓存失效与刷新统一收敛在业务 Hook，按资源关系处理；页面回调只处理分页、关闭弹窗、导航等页面行为，不重复刷新同一操作的数据。仅属于单个业务组件的操作可在该组件的 mutation 中处理刷新。
- 服务端资源变更后统一通过 `invalidateQueries` 或 `refetch` 获取最新数据，不使用 `setQueryData`、`setQueriesData` 将操作响应直接写入资源缓存，也不假设删除接口返回更新后的资源。
- 删除成功后使相关列表查询失效，由活跃列表重新请求；对应详情缓存只标记失效，不立即请求可能已不存在的资源，详情页按既有交互返回。操作后仍展示详情时刷新详情，并使受影响列表失效。需要将刷新纳入 mutation 完成阶段时，在 `onSuccess` 中返回或等待刷新 Promise；外部回调不得绕过 Hook 的刷新。
